# SR&ED — what FieldQuo is claiming, and why it qualifies

This folder is the contemporaneous record for a Scientific Research and
Experimental Development claim by FieldQuo Inc. It exists because a claim
reconstructed from memory at tax time is the one the CRA rejects, and one that
grew beside the work is the one it accepts.

- `LOG.md` — every commit in the five R&D projects below, dated, regenerated by
  `node scripts/build-sred-log.mjs` after each merge. Nothing in it is typed
  by hand; it is read from git.
- This file — the technological uncertainty each project set out to resolve,
  the hypotheses tried, and what was learned. **Update the "what we learned"
  lines when a project changes direction** — that sentence is the claim.

What is deliberately NOT here: payments, scheduling, invoicing, settings,
marketing pages, i18n plumbing. That is routine engineering under known
methods and it is excluded from the log by construction (the script reads only
the R&D paths). Claiming it would put the whole claim at risk.

## Eligibility, in one paragraph

SR&ED work is a systematic investigation, by experiment or analysis, to resolve
a *technological* uncertainty — a problem that standard practice and available
knowledge did not solve. The test is not "was it hard" but "did we not know
whether or how it could be done, and did we work through hypotheses to find
out". Each project below states that uncertainty in that form.

## P1 · Autonomous voice receptionist

**Uncertainty.** Whether a model-driven agent can take real bookings and
intake on a live phone line — with the latency, interruptions and partial
transcripts of telephony — without asserting availability, prices or facts it
does not hold, and hand off to a human under a crisis rule, in English,
French and Spanish.

**Hypotheses tried.** Free-form prompting (rejected: invented facts); tool-only
answers with refusal defaults; a prompt-shape retry that names the failing
line; per-call language selection; a crisis rule reduced to the owner's exact
instruction after broader rules produced wrong hand-offs; call-outcome
reconciliation against provider webhooks after the outbound drainer dialled
the same person twice.

**What we learned so far.** Refusal has to be the default state of every tool,
not a rule in the prompt; latency budget decides what the agent may look up
mid-call; a single retry with the failure named recovers most shape failures
and a second retry recovers almost none.

## P2 · Evidence-grounded capability detection (web crawler)

**Uncertainty.** Whether a crawler can state, per business, which capabilities
it truly has (online booking, payments, reviews, a real website vs a directory
listing, services offered) with cited evidence and *refuse to claim absence*,
across JavaScript shells, directory platforms, inline third-party loaders and
mixed-language sites — where naive crawling produced confident false claims.

**Hypotheses tried.** Keyword presence (rejected: false positives from menus
and footers); navigation ranking with absence refused on a guessed crawl;
three-valued verdicts (present / absent / unknown) with evidence spans;
siteKind detection so a directory page is never read as the business's own
site; structured sources first (sitemap, JSON-LD, WordPress REST, SPA
payloads) with a `js_shell` verdict when nothing renders server-side; a 50-site
hand-checked live read used as the acceptance set.

**What we learned so far.** "Unknown" must be a first-class answer or the
system lies; the cheapest reliable signal is the site's own structured data,
not its prose; a directory URL in a listing is the single largest source of
false capability claims.

## P3 · Structured extraction from conversations

**Uncertainty.** Whether an unstructured phone or chat conversation can be
turned into a priced draft quote and a lead with usable confidence, without
fabricated scope, and whether a conversation's "temperature" can be scored by
what was said rather than by how much was written.

**Hypotheses tried.** Direct transcript-to-quote generation (rejected: invented
line items); extraction into a constrained intermediate ("what the caller
asked for" vs "what the draft could place"), with the remainder carried as
internal review notes rather than onto the document; scoring rubrics keyed on
statements, not length.

**What we learned so far.** The extraction has to have a place to put what it
could not place; otherwise the model puts it on the quote.

## P4 · Constrained AI review of commercial documents

**Uncertainty.** Whether a model can improve the wording of a legally
meaningful document (a quote a homeowner signs) under hard constraints — it
may propose words but never a number, never a measurement or material from a
photograph, and never treat text inside an image as an instruction — and
whether those constraints can be enforced by the vendor's schema rather than
by prompt wording, and measured.

**Hypotheses tried.** Prompt-only rules (rejected: drift); strict JSON schema
mode with nullable-not-optional fields; isolating photo rules to a paid,
separate pass so the text review cannot describe a picture it never saw;
holistic completeness checks that read the document the way the client does
(scope paragraph + inclusions + lines) instead of line by line.

**What we learned so far.** Strict schema removes a class of failure entirely
but cannot express minimum lengths or counts, so post-validation stays; a
model shown the whole document stops proposing the scope paragraph back as a
longer line name.

## P5 · Multilingual generation under shape rules

**Uncertainty.** Whether call scripts, playbooks and site copy can be generated
in EN/FR/ES that reliably satisfy length, persona and no-invented-fact rules —
17 of the first 73 paid scripts were discarded for a single line-length rule.

**Hypotheses tried.** Post-hoc trimming (rejected: broke meaning); the
lead's-language-first pipeline with the other two written from it; a shape
rule retry naming the offending line; block lists and service names merged
back from the database after generation so the model writes sentences only.

**What we learned so far.** Generate in the target language, never translate
the document; give the model no freedom over structure and it stops breaking
it.

## How to keep this current

1. Any commit that tests a hypothesis in one of these projects goes in the
   listed paths — the log picks it up. If a new R&D thread starts elsewhere,
   add its path to `scripts/build-sred-log.mjs` and a section here.
2. When a hypothesis fails, say so in the commit message. Failed attempts are
   the strongest evidence of systematic investigation.
3. Re-run `node scripts/build-sred-log.mjs` after merging; commit the result.
4. At year end, hand this folder and the payroll/contractor records to the
   preparer. Salaries of the people who did this work, and 80% of contractor
   invoices for it, are the expenditures.
